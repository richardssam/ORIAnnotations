## 9. Defects found after this list was written

Everything below was found *after* sections 1-7 were complete and ticked — first
by the code review, then by live two-peer testing. All are fixed. They are
recorded because the list otherwise claims this change cost 42 tidy steps, when
the honest figure is that leasing a category which had been a fixed seat for the
session's whole history shook out twelve further defects. Several were
pre-existing bugs that only became reachable once the seat could move.

### From the code review

- [x] 9.1 **The visibility resolver was not associative.** A pairwise "within `VISIBILITY_HOLDOFF`" test is a tolerance comparison, and folding three claims through it gave three different winners depending on arrival order — with peers folding in different orders, since each applies its own claim before broadcasting it. Two peers then both believed they held the category. *Fixed:* resolution is a plain total order (`min` on `(-claim_ts, guid)`); the hold-off moved to the claim site, where a withheld claim is simply absent from every peer's fold. `test_resolve_claim_is_order_independent` is parametrized over every channel.
- [x] 9.2 **RV's highlight-only selection claimed visibility.** `on_selection_changed` reaches `broadcast_view_state`, and its own comment calls RV's selection "a loop/highlight concept, not a view switch" — but claiming made its `clip_guid` survive the strip, so a highlight moved the session's shot. *Fixed:* `asserts_view=False` on that path, with the distinction in the parameter so a new caller has to answer it.
- [x] 9.3 **`drop_peer` re-elected but did not release the departed peer's leases.** Its own docstring says re-election exists so a departed host cannot freeze the view; with visibility leased, the lease outlived the peer and froze it anyway for up to 3 s. *Fixed:* `_release_peer_leases` frees every channel through the normal expiry path, so a queued claimant is granted by the usual rule.
- [x] 9.4 **The session panel reported expired leases as live.** Expiry is lazy and the projection read `_leases` without settling it, so the one surface whose job is to name the holder showed an idle one indefinitely. *Fixed:* settle before reading, as every other lease reader does.
- [x] 9.5 **`resolve_claim`'s docstring overclaimed.** It promised agreement "without synchronized clocks" — true of earlier-wins, not of a hold-off comparing wall-clock stamps across machines. *Fixed:* it now states what ordering actually guarantees under skew, that every peer reaches the *same* winner from the same claims.
- [x] 9.6 **A second guess at "was this local?" was worse than none.** The review flagged that claiming before reading `owns_visibility()` made the check self-fulfilling; sampling before the claim fixed that but introduced a subtler fault, since the answer is "no" for the first clip any peer isolates — it cannot hold a lease it is in the act of taking. *Fixed:* the predicate is gone; provenance is established at the call sites, all four of which gate on `_is_remote`. **Worth keeping:** a guard that fires on the most ordinary case it will ever see is not defence in depth, it is a second failure mode.

### From live two-peer testing

- [x] 9.7 **A view announcement re-broadcast a peer's old frame.** `broadcast_view_state` substituted "the position the driver last told us" when it could not vouch for its own — a no-op only until either peer moves. After this peer scrubbed 16→160 it announced `frame=45`, and the session followed onto a frame nobody was on. *Fixed:* withholding now means **omitting the position group**, which both plugins already read correctly as "said nothing"; the substitution and the `_last_received_frame` feeding it are deleted.
- [x] 9.8 **A position-stripped message silenced the peer that was driving.** The echo guard armed on *any* playback message, reasoning that receiving one means a peer is driving. A message whose position was stripped says nothing about position — so a peer explicitly not driving silenced the one that was, dropping two scrubs and leaving the peers 116 frames apart. *Fixed:* the guard arms only when the message actually asserts a position.
- [x] 9.9 **An isolation reset the local playhead and announced a different frame.** The reset ran unconditionally; only the *announcement* was gated on a guess. *Fixed:* both unconditional. **Worth keeping:** gating one half of a two-part action on a predicate is itself the defect — the frame you move to and the frame you announce must be the same frame.
- [x] 9.10 **A paused scrub across a sequence was read as a clip isolation.** `_is_scan_through` asked `_last_polled_playing`, so a user *dragging* the playhead through edits escaped it and every crossing forced frame 0 — the peer received `0, 0, 208, 0, 0, 0, … 227, 0`. *Fixed:* a moving playhead is scan-through whether or not it is playing, and an isolation additionally requires a playhead at rest.
- [x] 9.11 **Joining changed what the session was viewing, then failed to adopt it.** A free visibility lease let a joiner claim the category, and its build put the *first* clip on screen, which it broadcast at frame 0. Fixing that exposed the real requirement — a joiner should *adopt* the host's view. The snapshot carried `current_time` and no `view_mode`/`clip_guid`; once it did, the seek still died with the playhead the joiner's own view switch had replaced. *Fixed:* the on-screen-source call arms the echo guard, `STATE_SNAPSHOT` joins the view-inducer table, `current_playback_state()` carries the view, `apply_join_playback_state` adopts it once a playhead exists, and a seek lost to a replaced playhead is deferred rather than dropped.
- [x] 9.12 **A `-1` sentinel for "no frame" was considered and rejected.** xStudio clamps with `max(0, …)` and OpenRV adds the frame base, so it would arrive as frame 0 on one host — the very bug — and `base - 1` on the other. `authority.position_frame` returns `None` instead, and closes the malformed-`current_time` case the group-presence check cannot see.
